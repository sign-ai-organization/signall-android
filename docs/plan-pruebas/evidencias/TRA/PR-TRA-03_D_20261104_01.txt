5. EL SERVICIO STT DEL COMPOSE DE PRUEBA NO SE LEVANTÓ (y por qué)
==============================================================================
`docker-compose.yml` del backend construye el STT desde `../sign-ai-stt` y lo
levanta con reserva de GPU:

  deploy: resources: reservations: devices: [driver: nvidia, count: 1, gpu]

Estado medido de la GPU al empezar:

  NVIDIA GeForce RTX 4050 Laptop GPU · 6141 MiB totales · 2011 MiB en uso ·
  3843 MiB libres
  proceso GPU: pid 503423 /usr/local/bin/python3.11 (el STT de la tesis,
  whisper `medium` en CUDA)

No se levantó el segundo STT a propósito: cargar otro `medium` float16 en los
3,8 GB libres podía provocar un OOM de CUDA y desestabilizar el STT que la
sesión de STT de la ronda está usando. El encargo de esta prueba autoriza
explícitamente esta salida (§3: "Si el servicio stt no puede levantar (GPU
ocupada...), apuntá el backend al STT que ya corre y anotá el paso").
Consecuencia honesta: el tiempo de build de la imagen `stt` NO se midió, y el
test valida el backend contra el STT real, no contra un STT recién construido.

7. ¿NECESITÓ LA RED DEL EQUIPO ANFITRIÓN? (medido, no supuesto)
==============================================================================
Prueba de conectividad desde un contenedor en la red bridge normal, con
`--add-host host.docker.internal:host-gateway` (lo mismo que declara el compose):

  host.docker.internal:11434  (Ollama del host)  -> TimeoutError: timed out
  172.17.0.1:11434            (gateway directo)  -> TimeoutError: timed out
  host.docker.internal:8000   (STT del host)     -> OK
  1.1.1.1:443                 (control, internet) -> OK

Consecuencia medida:
  - Para el STT y para Neon, la red de compose alcanza; NO hace falta red host.
  - Para el LLM NO alcanza en esta máquina: el Ollama del host (11434) está
    filtrado por el firewall del equipo, tal como advierte el comentario de
    `docker-compose.yml`. El síntoma en el backend es:

      WARNING app.nlp.llm_client: LLM warm-up failed; the first real phrase
      will pay the model load
      (TimeoutError: Request timed out., tras 10,4 s)

    Es decir: /health responde, pero con la red de compose el backend NO puede
    traducir nada porque no llega al modelo. Para un backend funcional en esta
    máquina hace falta `docker-compose.host.yml` (red host) o abrir el firewall.
  - El backend de la tesis, de hecho, corre con la variante de red host: su
    entorno tiene STT_WS_URL=ws://127.0.0.1:8000 y
    LLM_BASE_URL=http://127.0.0.1:11434/v1.

Respuesta a la métrica "si el contenedor necesitó la red del equipo anfitrión
(no debería)": para responder /health, NO. Para funcionar de verdad (LLM),
SÍ, en esta máquina, o hay que abrir el firewall para la subred de docker0.
No se pudo probar `docker-compose.host.yml` porque toma el 8080 del host, que
está ocupado por el backend de la tesis y no se podía reiniciar.

10. LO QUE NO SE PUDO MEDIR (dicho explícitamente)
==============================================================================
  a) Build de la imagen Docker del backend EN FRÍO (sin caché de capas). La
     imagen pesa 10 GB porque instala torch; el disco de la máquina tiene
     8,6 GB libres de 473 GB (99 %), así que un `--no-cache` no cabe. El 4,1 s
     medido es un piso, no lo que tardaría en una máquina limpia.
  b) Build de la imagen del STT: no se levantó el servicio (§5), así que ni se
     construyó.
  c) Ruta `docker-compose.host.yml`: publica el 8080 del host, ocupado por el
     backend de la tesis, que no se podía reiniciar.
  d) No se probó una traducción de punta a punta contra este backend de prueba:
     el LLM no es alcanzable desde la red de compose (§7), y además escribiría
     en la base de Neon compartida.
